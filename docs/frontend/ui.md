# Frontend UI guidelines

Applies to shared UI, owned Spartan Helm components and feature presentation. Paths are relative to `frontend/`. Read the [Angular conventions](angular.md) and [template style](../styleguide.md#typescript-and-angular-templates).

## Components, styling and themes

- Use Spartan components and their built-in variants first whenever an equivalent primitive exists, including Tabs with the Line variant, Toggle Group, form controls, dialogs, cards, empty/error states and loading indicators. Do not recreate their appearance, selection state or accessibility behavior with custom markup. Before implementing or changing UI, review the installed components and Spartan catalog; generate missing components in the configured shared Helm library structure. Compose or adapt the owned Helm components when needed. Custom UI is appropriate only when no Spartan component meets the requirement; keep that choice explicit in the implementation or review.
- Use Tailwind CSS v4 for styling. PostCSS is configured in `.postcssrc.json`; shared theme tokens are in `libs/shared/ui/src/theme/styles.css`, registered before application CSS in each app’s `project.json` build `styles` array; do not repeat relative theme imports in application CSS.
- Prefer canonical utilities supported by the installed Tailwind version: for example, `aspect-3/1`, `h-lh`, `max-w-304` and `scrollbar-gutter-stable` instead of equivalent arbitrary-value classes. Check Tailwind CSS IntelliSense canonical-class suggestions when changing templates, component host classes or `@apply` rules. Use arbitrary values only when no equivalent utility exists; confirm equivalence against the project theme and preserve intentional custom values. Resolve new canonical-class warnings before finishing UI changes.
- Tailwind source detection excludes `frontend/.agents` through the shared theme stylesheet. Agent documentation examples must not contribute application CSS; keep application and Helm component sources included.
- Component stylesheets using `@apply` reference the shared theme with `@reference '#theme.css';`. The CSS subpath alias is defined once in the frontend `package.json` imports map; avoid relative paths to the shared theme. `@reference` exposes theme definitions during compilation without emitting the theme again.
- Theme selection uses a head `<meta name="color-scheme">`: `light`, `light dark` for the default/system choice, or `dark`. Use CSS `light-dark()` semantic tokens rather than toggling a `.dark` class. Keep Tailwind dark variants aligned with the meta value and system preference.
- Keep browser chrome hints aligned with the selected theme using two `theme-color` meta tags: white (`#ffffff`) and dark zinc (`#09090b`). In system mode use their `prefers-color-scheme` media queries; for an explicit choice enable only its tag with `all` and disable the other with `not all`. Apply these hints both in the startup script and at runtime. Browser UI coloring is best-effort and depends on browser/platform support.
- Admin persists `game-atlas.theme` (`light`, `system`, `dark`) as a raw string through ngxtension `injectLocalStorage`; the startup script at the beginning of `<body>`, before `<app-root>`, only reads the same key before Angular bootstraps. Keep browser persistence in the application; shared theme controls expose signal inputs/models.
- Use Material Symbols Rounded consistently, including icons inside owned Spartan Helm components. Import SVG icons from `@ng-icons/material-symbols/round` and register only the icons used with `provideIcons`. Do not load external icon fonts or mix icon families. Keep decorative icons hidden from assistive technology and give icon-only controls accessible names.
- Keep owned Spartan Helm code in separate buildable Nx libraries under `libs/shared/ui-helm/<component>`, each tagged `type:ui`, `scope:shared`, `platform:shared`. Each primitive, including `utils`, has its own Nx project and `src/index.ts`; there is no enclosing `ui-helm` project. Keep our reusable components under `libs/shared/ui/src/lib` in the non-buildable `shared-ui` project, grouped by functionality without an extra `components` directory. Its public API remains `@game-atlas/shared/ui`. Use `generateAs: library`, `buildable: true` and `componentsPath: libs/shared/ui-helm` in `components.json`. Import specific Helm libraries (`@spartan-ng/helm/button`, etc.). The `shared-ui` project may consume Helm; Helm must not depend on GameAtlas components. Nx builds required Helm dependencies before consumers.
- Spartan UI dependencies and theme are configured. `components.json` defines the destination and import alias for any future Helm components.
- Reuse existing project components and library APIs. Generate missing Spartan Helm components when needed for the requested feature, following the configured library structure under `libs/shared/ui-helm`.
- Use Spartan tooltips instead of native `title` hover hints. Do not repeat fully visible text in a tooltip. Responsive labelled actions show hints only when their labels are hidden; truncated names or additional error details may still need tooltips. Add `uiTooltipOnOverflow` alongside `hlmTooltip` for text that needs a hint only when clipped. Reuse a primitive's existing tooltip input when it already hosts BrnTooltip; do not apply a second tooltip directive to the same element.
- Use shared `button[ui-button]` / `a[ui-button]` for ordinary action controls. It composes HlmButton, accepts `loading` and optional `icon: IconType`, retains hidden content under the spinner and prevents activation while disabled/loading. Keep specialized menu and sidebar primitives on their own directives.
- Pages contribute breadcrumbs and actions to the application header through the shared page-header portal/outlet. Keep the header's layout and theme controls in the application shell.
- Shared Helm tooltips use a 500ms touch hold, never touch-origin focus from a short tap. Cancel on release, movement/scroll or pointer cancellation; consuming a recognized hold must prevent accidental control activation. Preserve mouse hover and keyboard focus, and compose the same behavior into specialized tooltip hosts.
- Busy buttons retain their original label/content with `visibility: hidden` and overlay a spinner. Preserve their width and height; do not replace labels with Saving/Moving text.
- Use semantic colors and existing component variants. The shared `ThemeSwitcher` remains a controlled UI component. Helm entrypoints and UI-specific helpers, including `@spartan-ng/helm/utils`, stay in their buildable libraries under `libs/shared/ui-helm`, with separate project/configuration files per primitive. See [Angular conventions](angular.md) for browser render hooks.

## Resource screens

- Use Spartan Select for choices, including filters and Signal Forms; do not style native select elements as text inputs. Follow the installed select composition, including hlmSelectPortal.
- Resource list loading uses skeletons matching the eventual cards or rows. Empty states compose Spartan Empty. ErrorState content must use uiErrorStateHeading and uiErrorStateDescription slots, with the same icon/action composition as Media.
- Keep filter labels accessible without adding a visible label row when placeholders and named triggers communicate the controls. Prefer a compact combined sorting control when it avoids redundant fields.
- Use navigation appropriate to the editor layout: a named back-arrow beside the title for compact editors, or a Cancel action beside Save/Create in the workspace header for full settings pages. Put status beside the title and avoid a redundant All games action. Header submit buttons target the editor form by its stable form ID.
- Reusable confirmation and picker dialogs belong to shared UI. Data-driven shared dialogs own injectQuery/injectMutation and depend on a shared port, not a domain QueryOptions class. Implement the adapter in the owning domain and provide it at application level.

## Category tree

Show Categories below styles in the same left panel. Group rows contain handle, expansion arrow, optional icon, name, marker count and actions; indented children contain handle, optional icon, name, count and actions. Counts/actions stay visible while names truncate. Missing icons do not show broken images.

Use Angular Aria Tree because Spartan has no installed tree. Retain project theme tokens and Material Symbols Rounded. Use labelled CDK handles, allow empty/collapsed destinations, and provide Move up/down and Move to group menu alternatives. Preserve focus and show failures locally. Category writes currently await persistence and exact tree invalidation; optimistic behavior is deferred.

The category header uses a Spartan Button Group with two independent icon-only ghost buttons with accessible names and Spartan tooltips: plus for Add category and folder-plus for Add group. There is no creation dropdown; Add category retains prerequisite guidance when no group exists. Add and row menus include decorative Material Symbols icons. Both groups and categories expose hex colors; category colors are optional and nullable; an absent color preserves the original icon without a mask or outline. Iconless rows display filled map-pin fallback icons for categories; groups without library images render no icon.

The map editor left panel fills its available height and uses four Spartan accordion sections in order: Map styles, Categories, Markers, Settings & Tools. Headers are 40px tall with leading Material Symbols icons; creation actions are icon-only ghost buttons separate from the labelled section trigger, before its far-right chevron. Only Map styles starts open; at most one section is expanded and all can be collapsed. The expanded content receives remaining height and scrolls internally while all headers remain reachable. Keep creation controls outside accordion trigger buttons and register style/category scrollers with CDK for drag auto-scrolling.

## Marker editor

Use a native Spartan Drawer below md and a nonmodal right-side panel above it with the same Signal Forms draft across breakpoint changes. The desktop panel has a labelled close button and Escape handling, keeps map/list interactions and keyboard access available, and guards dirty changes when switching markers. Keep the form scrollable and actions visible. Native swipe dismissal follows the same dirty/pending protection as closing and navigation; do not add snap points or fullscreen expansion. The selected marker stays fully visible with padding in the map region above the measured mobile Drawer, using minimal pan and unchanged zoom.

Group category choices with Spartan Select and render image icons or colored map-pin fallbacks in both options and selected value. Marker photographs use a manual Spartan Carousel with library image selection, detach and keyboard-reachable ordering; plain-text descriptions have no formatting toolbar. Keep existing video attachments represented when editing photos.

The bottom map toolbar orders Pan, Move marker, Add marker and Add several markers, with two separate creation buttons and no selection dropdowns. Move persists only on changed drag release; repeated Add uses a validated template and saves each intentional click immediately until Finish/Escape. Provide named controls, visible active mode, keyboard-reachable rows in the separate left Markers accordion and numeric X/Y editing as a drag alternative. Placement failures remain distinguishable and never automatically repeat a POST with an uncertain outcome.

The left Markers accordion uses the available content height when it is the sole expanded section and scrolls independently. Rows show category icons, marker names and category names. Keep loading, empty and retry states local to this section. Selecting a marker on mobile closes the content panel before opening its Drawer.

Settings & Tools contains only a labelled Map name field with an icon-only Save action (diskette) in a trailing Spartan Input Group addon, with an accessible name and tooltip. Use the existing map update mutation, require 1..200 trimmed characters, skip unchanged PATCHes, retain failed input and prevent duplicate submission. Preserve the draft when switching sections or hiding the panel. Successful saves update the existing cache and breadcrumbs. Map-list modal rename remains available.

The content-panel toggle belongs immediately before the map style selector and stays available with zero or one style. Desktop starts with the panel visible; mobile starts hidden and has an accessible close control inside the open panel; do not add a separate map-name/content-toggle header above the viewport. Hiding preserves the expanded section and drafts, restores focus to a visible control, and resizes the viewport without resetting center, resolution or style. Do not persist panel state between reloads.

Animate content-panel hiding/showing with a 200ms slide and opacity transition; respect reduced motion. Make closed panel content inert immediately and preserve focus restoration. Its map toggle uses directional left/right chevrons to distinguish it from the application sidebar toggle.

Use Tailwind utilities for the content-panel transition, responsive negative inline margin, opacity, visibility and reduced motion. The map-name form model is initialized per map ID and preserved across updates for that map; successful saves explicitly adopt the returned name and reset the form. Keep this independent of optimistic mutation state.

Do not show inactive search/filter buttons in the map editor toolbar. Keep its panel toggle, flexible style selector and working map controls on one row at 320px and above. Allow the selector and selected label to shrink/truncate while preserving control sizes and accessible names.

Fullscreen in the map editor expands the whole workspace containing the map and both editing panels. Preserve panel visibility, section selection and drafts on entry/exit; selects, dialogs and mobile drawers must remain available inside fullscreen. Shared viewport consumers may supply a containing fullscreen target, with the viewport host as the default.
